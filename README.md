## 記事の概要

- 今回は続編記事です。前回の記事article_requirements_driven_ai_dev.mdを読んでください。
- 今回は仕様駆動開発の元祖とも言えるkiroとの比較を行います
- kiroは残念ながら仕様に必要な情報を集めず、質問せずに仕様を書いてしまいます
- kiroの書く仕様は、WHEN IF THEN 形式で書かれていますが、人間には理解に時間がかかり、プログラムに近い仕様になってしまいます
- EARS 形式：WHEN / IF / THEN の形式で記述され、AIには読みやすく理解しやすい
- kiroに従って不十分な情報でEARS形式の仕様書を書いてもらい、多少の修正をして、設計から実装は一気にやってもらいました。
  - その結果、設計も不十分なものになり、実装が動かない状態で、結局動く様になりませんでした
- kiroを使って、要件定義の際に、私のプロンプトを使って、必要な情報を集めて、私が定義した目次の要件定義書を作り、
  その要件定義書を元に、私のプロンプトを使って、私の定義した目次設計書を作ってもらい、実装もしてもらいました。
    - その結果、設計も十分なものになり、一発で動く実装を作ってくれました
- まとめ：仕様駆動開発と言っても仕様をどのように作るか、それをもとに設計をどのようにすべきかをAIに伝えておかないと
  不十分な要件と設計で実装してしまい、結局vibeコーディングと同じ末路になってしまうことがわかりました
- 今回作ったプロンプトの威力が結構すごいので、びっくりしました。事務用アプリについてはSystem Engineerの仕事が代替されるレベルだと思います。ぜひみなさんも試してみてください。
- プロンプトの内容はリポジトリに公開していますので、ぜひ見てみてください

現状のプロンプトに足りないと思っていること：
- 既存コードからの設計書作成→仕様書作成のプロンプトと仕組み
- e2eテストの作成をするプロンプト
 - 要件定義の時点でテスト用のシナリオを作成、ユーザーが確認**これ重要**
   - GUIの場合playwright必須でdocker composeでe2eテストするように設計書で強制
- 社内のプロキシ、証明書などの環境依存の情報を要件定義書・設計書に入れるためのプロンプトと仕組み
- 外部システム、DBとの連携
  - 要件定義の時に聞いてくれるが、設計書を書く際に外部システムのAPI仕様やDBのスキーマを参照して設計するように指示するプロンプトと仕組み
    - MCPを使ってOpenMetaDataとか、社内のDBスキーマストアとか、API仕様書ストアから仕様を取ってこれるようにする
    - その上でe2eテストのためのモックの作り方を設計書に入れるようにする
- 要件仕様、設計にログ設計も入れるようにしたい

# 技術ブログ執筆チェックリスト（Qiita等）

## ✅ 1. 目的と対象読者
- [ ] 記事の目的は明確か（例：チュートリアル、検証結果、ベストプラクティスの共有など）
- [ ] 対象読者の技術レベルを意識しているか（初心者向けか、中級者以上か）
- [ ] 読者の課題や興味と記事内容が一致しているか

## ✅ 2. 構成・見出し
- [ ] 導入文で記事の概要・背景が説明されているか
- [ ] 各セクションに明確な見出しがあるか
- [ ] 「やること」と「結果」が明確に分けられているか
- [ ] まとめ・所感・次のステップがあるか

## ✅ 3. 技術内容の正確性
- [ ] コードや設定は実際に動作検証されているか
- [ ] バージョン情報や前提条件が明記されているか（OS, ライブラリ, ツールなど）
- [ ] ソースや公式ドキュメントの参照があるか
- [ ] 再現可能な環境構築手順が書かれているか（例：Dockerfile, 仮想環境設定）

## ✅ 4. 可読性・表現
- [ ] 専門用語に説明がついているか
- [ ] 図やスクリーンショット、表を活用して視覚的に補足しているか
- [ ] 日本語の表現が自然で、誤字脱字がないか
- [ ] コードブロックが整形されていて読みやすいか

## ✅ 5. 問題解決の文脈
- [ ] 解決しようとした課題・問題が明示されているか
- [ ] 試行錯誤の経緯（成功・失敗）も記述されているか
- [ ] 問題発生時のログやエラーメッセージが提示されているか
- [ ] 解決策が根拠を持って説明されているか

## ✅ 6. キーワード・SEO対策
- [ ] 検索されやすいキーワードをタイトルや冒頭に含めているか
- [ ] タグが適切に設定されているか（Qiitaタグ機能など）
- [ ] 同様の記事との差別化ポイントが明記されているか

## ✅ 7. メンテナンス・更新性
- [ ] 記事が古くなる可能性のある技術については注記があるか
- [ ] 想定外の動作や注意点についても記載しているか
- [ ] コメントやフィードバックへの対応を想定しているか
